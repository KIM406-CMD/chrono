# Online Supermarket System - Database Design

> [简体中文](../zh/db-design.md) | English

---

## 1. Design Principles

| Principle | Description |
|------|------|
| Deletion strategy | Physical deletion (delete records directly) |
| Image storage | Store URL path strings; at most 4 per product |
| Product snapshot | No snapshot; orders reference `product_id` / `sku_id` and fetch the latest information in real time when queried |
| Refund granularity | Supports partial refunds, linked to `order_item` |
| Address storage | Province/city/district stored as plain text (manually entered by the user) |

| level | TINYINT | Level: 1/2/3 |

### `spec_template` Specification Template Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| name | VARCHAR(50) | Specification name (e.g., "Color", "Size") |
| created_at | DATETIME | Creation time |

### `spec_value` Specification Value Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| template_id | BIGINT FK | References `spec_template` |
| value | VARCHAR(50) | Specification value (e.g., "Red", "XL") |

> **Status**: Specification templates/values are reserved tables; merchants currently submit a SKU list directly (`product_sku.spec_text` / `spec_ids`), and no template management API is provided yet.

### `product` Product Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| name | VARCHAR(200) | Product name |
| description | TEXT | Product description (rich text) |
| images | VARCHAR(2000) | Image URL array (JSON, at most 4) |
| brand | VARCHAR(100) | Brand |
| category_id | BIGINT FK | References a three-level category |
| merchant_id | BIGINT FK | References the `merchant` table |
| status | TINYINT | 0-Unlisted, 1-Listed |
| sales | INT DEFAULT 0 | Cumulative sales |
| created_at | DATETIME | Creation/listing time |
| updated_at | DATETIME | Update time |

> **Note**: The basic product information stores only descriptive fields; price and stock are pushed down to SKUs. The `sales` field uses a Redis counter and is periodically synchronized back to MySQL to avoid high-frequency database writes.

### `product_sku` SKU Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| product_id | BIGINT FK | References the `product` table |
| spec_ids | VARCHAR(200) | Specification value ID combination (JSON array, e.g., `[1,5]` means "Red + XL") |
| spec_text | VARCHAR(200) | Specification text (e.g., "Red/XL") for display convenience |
| price | INT | Price (unit: cents) |
| stock | INT | Stock quantity |
| status | TINYINT | 0-Disabled, 1-Enabled |
| created_at | DATETIME | Creation time |

> **Note**: When publishing a product, the merchant selects specification templates and their corresponding values, and SKUs are generated by combination. The stock of popular product SKUs can be cached in Redis; at order time, Redis stock is deducted first and asynchronously synchronized to MySQL.

## 7. Product Comments

### `comment` Comment Table (Multi-level Nesting)

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| product_id | BIGINT FK | References the `product` table |
| user_id | BIGINT FK | References the user table |
| order_item_id | BIGINT | References `order_item` (has a value when reviewing after purchase; traceable source) |
| parent_id | BIGINT | Parent comment ID; NULL means a first-level comment, non-NULL means a reply |
| content | VARCHAR(1000) | Comment content |
| star | TINYINT | Star rating (1-5); only first-level comments have a value, replies are NULL |
| is_append | TINYINT | 0-First comment, 1-Follow-up comment |
| status | TINYINT | 0-Normal, 1-Deleted (deleted by administrator/merchant) |
| created_at | DATETIME | Comment time |

> **Overall design rationale**:
> - Currently only users with a received order can post a first-level comment; merchants can reply to comments on their own products.
> - After the user confirms receipt, a star rating window pops up; after submission, a comment with `star + is_append=0` is generated. The user can later comment on the same product again, with `is_append=1`, implementing a follow-up comment.
> - The current implementation uses two levels: top-level comment + follow-up review/merchant reply (linked by `parent_id`); unlimited nesting is not implemented.
> - `status` is reserved for soft deletion (0-normal, 1-deleted); no comment deletion API is provided yet.
> - Redis comment statistics and ES synchronization are planned, not implemented yet.

## 9. Instant Messaging (WebSocket Chat)

### `conversation` Conversation Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| user_id | BIGINT | Regular user ID, references the user table |
| merchant_id | BIGINT | References the merchant table primary key (merchant.id), not user_id |
| product_id | BIGINT | Associated product ID (optional; marks which product the conversation originated from) |
| last_message | VARCHAR(500) | Summary of the last message |
| last_message_time | DATETIME | Time of the last message |
| user_unread | INT DEFAULT 0 | User unread count |
| merchant_unread | INT DEFAULT 0 | Merchant unread count |
| created_at | DATETIME | Creation time |
| updated_at | DATETIME | Update time |

> **Note**: There is only one conversation between the same user and the same merchant. A unique constraint on `(user_id, merchant_id)` prevents duplicate creation. When a user clicks "Contact Seller" from the product detail page, `product_id` is passed; if the conversation already exists, this field is ignored.

### `message` Message Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| conversation_id | BIGINT FK | References the `conversation` table |
| sender_id | BIGINT | Sender ID, references the user table |
| sender_role | TINYINT | Sender role: 0-User, 1-Merchant |
| content | VARCHAR(2000) | Message content |
| type | TINYINT | Message type: 1-Text, 2-Image |
| is_read | TINYINT | 0-Unread, 1-Read |
| created_at | DATETIME | Send time |

> **Note**: Offline messages: when the sender sends a message, it is written to the database; after the receiver comes online, unread messages are pulled from the database and pushed via WebSocket. A scheduled task cleans up messages with `created_at < 30 days ago` at midnight every day.

## 10. Flash-sale Coupons and User Coupons

### `seckill_coupon` Flash-sale Coupon Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| name | VARCHAR(100) | Coupon name |
| description | VARCHAR(500) | Coupon description |
| discount_type | TINYINT | Discount type: 1-Full reduction coupon, 2-Discount coupon |
| discount_value | INT | Discount value: for full reduction coupons, the reduction amount (cents); for discount coupons, the discount value (e.g., 85 means 85% of the original price, i.e., a 15% discount) |
| min_amount | INT | Minimum spending amount (cents); 0 means no threshold |
| total_count | INT | Total quantity issued |
| remain_count | INT | Remaining quantity |
| start_time | DATETIME | Campaign start time |
| end_time | DATETIME | Campaign end time |
| per_user_limit | INT DEFAULT 1 | Claim limit per user |
| status | TINYINT | Status: 0-Not started, 1-In progress, 2-Ended |
| created_at | DATETIME | Creation time |
| updated_at | DATETIME | Update time |

> **Note**: `remain_count` is the final database stock. When claiming, decrement it atomically in Redis first, then synchronize the decrement to this field; if Redis is unavailable, degrade to atomic deduction with `UPDATE ... SET remain_count = remain_count - 1 WHERE remain_count > 0`. Status is refreshed by a scheduled task every 30 seconds according to the time window.

### `user_coupon` User Coupon Table

| Field | Type | Description |
|------|------|------|
| id | BIGINT PK | Primary key |
| user_id | BIGINT FK | References the user table |
| coupon_id | BIGINT FK | References the `seckill_coupon` table |
| status | TINYINT | Status: 0-Unused, 1-Used, 2-Expired |
| used_order_id | BIGINT | ID of the order that used this coupon; empty when unused |
| claim_time | DATETIME | Claim time |
| used_time | DATETIME | Usage time |
| created_at | DATETIME | Creation time |

> **Note**: The `(user_id, coupon_id)` composite index supports claim-limit validation and the "My Coupons" query; when a coupon campaign ends and the coupon is unused, a scheduled task batches it to "Expired".

### 12.19 Index Design Summary

| Type | Count | Description |
|------|------|------|
| UNIQUE indexes | 4 | username, order_no, user+sku, user+merchant |
| Regular INDEX (single-column) | 48 | High-frequency query fields |
| COMPOSITE indexes | 8 | Multi-condition high-frequency queries; covering indexes reduce table lookups |
| FULLTEXT indexes | 1 | MySQL full-text search fallback |
| **Total** | **61** | |

> **Note**: Composite indexes follow the **leftmost prefix principle**; the `WHERE` condition must include the first column of the composite index to use it. For example, `idx_category_status(category_id, status)` supports "query by category_id only" and "query by category_id + status together", but does not support "query by status only".

## 13. Redis Cache Design

> **Status**: The implementation currently uses `token:*`, `reset:*`, `captcha:*`, `category:tree`, `order:submit-token:*` and `seckill:*`; the remaining entries below are planned.

| Cache Key Example | Content | Data Structure | Expiration Strategy |
|------|------|------|------|
| `token:{userId}` | User login state | String | Set expiration time |
| `hot:products` | Home page popular product list | ZSet (sorted by sales) | Refresh periodically |
| `category:tree` | Three-level category tree | String (JSON) | Actively update when categories change |
| `hot:search` | Search hot words ranking | ZSet | Refresh periodically |
| `verify:{uuid}` | Graphical captcha | String | Expires in 5 minutes |
| `product:{id}:stock` | Product SKU stock | Hash | Deduct at order time; periodically synchronize to MySQL |
| `product:{id}:sales` | Cumulative product sales | Hash | Increment at order time; periodically synchronize to MySQL |
| `product:{id}:comments` | Comment statistics (total count + average star rating) | Hash | Update when comments change |
| `sku:{id}` | Popular SKU cache | String (JSON) | Set expiration time; invalidate on change |
| `seckill:remain:{couponId}` | Flash-sale coupon remaining stock | String | Expires 24h after the campaign ends |
| `seckill:claimed:{couponId}:{userId}` | Number of coupons claimed by the user | String | Expires 24h after the campaign ends |
