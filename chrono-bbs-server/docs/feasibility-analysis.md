### 2.2 关键技术风险分析

#### 风险 1：Elasticsearch（⚠️ 高风险）

| 风险项 | 分析 |
|--------|------|
| 风险描述 | 团队不熟悉 Elasticsearch，需要从零学习部署、中文分词、索引设计和 DSL 查询 |
| 依赖项 | Docker ES 镜像部署 → 中文分词器（IK Analyzer） → 索引映射设计 → 数据同步（MySQL → ES） → 前端 DSL 查询 |
| 影响范围 | 搜索功能（高优先级 F-10）和搜索建议/自动补全功能 |
| 学习曲线 | ES 概念较多（索引、映射、分词器、DSL），预计需 5-7 天学习 + 实践 |
| **缓解措施** | 1. 优先使用 Docker 快速部署 ES 和 Kibana（可视化调试）<br>2. 先完成商品基础 CRUD，再渐进式集成 ES<br>3. 搜索建议（自动补全）可作为降级目标，先用简单的 `LIKE` 查询兜底<br>4. 团队分工：指定 1 人专门负责 ES 调研与集成 |

#### 风险 2：WebSocket 即时通讯（⚠️ 中风险）

| 风险项 | 分析 |
|--------|------|
| 风险描述 | 后端使用 JSR 356 注解（@OnOpen / @OnMessage），前端原生 WebSocket API，需要处理连接管理、重连、消息分发 |
| 影响范围 | 即时通讯功能（低优先级 F-46 ~ F-47），不影响核心购物流程 |
| **缓解措施** | 1. 即时通讯设为低优先级，核心功能完成后再开发<br>2. 前端封装 `useWebSocket` composable，统一管理连接生命周期<br>3. 后端用 `ConcurrentHashMap` 管理用户连接会话<br>4. 消息格式简单（JSON），无需引入额外协议 |

#### 风险 3：Docker 容器编排（⚠️ 中风险）

| 风险项 | 分析 |
|--------|------|
| 风险描述 | 团队不熟悉 Docker，需要学习 Docker Compose 同时编排 MySQL + Redis + ES 三个服务 |
| 影响范围 | 开发环境和演示环境搭建 |
| **缓解措施** | 1. 先用本地安装方式开发（MySQL、Redis 直接安装），确保业务开发不被阻塞<br>2. 中期编写 Docker Compose 文件，一键启动所有中间件<br>3. Docker Compose 编排只需 1 个 `docker-compose.yml` 文件，学习成本可控（1-2 天） |

#### 风险 4：Redis 缓存与分布式锁（⚠️ 低-中风险）

| 风险项 | 分析 |
|--------|------|
| 风险描述 | Redis 需要实现登录态缓存、防重复提交 Token、分布式锁（下单）、商品销量计数等 |
| 影响范围 | 认证、下单、销售统计等多个高优先级功能 |
| 学习曲线 | 单机 Redis 基本操作简单，分布式锁有一定学习成本 |
| **缓解措施** | 1. 先使用简单的 `SET key value EX seconds` 实现登录态和防重 Token<br>2. 分布式锁用 Redisson 或手写 `SETNX` + Lua 脚本，参考网上的成熟方案<br>3. 销量计数用 `Redis INCRBY` 异步同步回 MySQL，简单可靠 |

### 2.3 技术可行性结论

| 结论 | 说明 |
|------|------|
| ✅ **整体可行** | 核心技术栈（Spring Boot + Vue + MySQL）是成熟且广泛使用的组合，社区资源丰富 |
| ⚠️ **有风险但可控** | ES 和 WebSocket 有学习成本，但都有缓解措施，且 WebSocket 已降为低优先级。只要合理分配学习时间，不影响核心功能交付 |
| 📋 **关键要提前做** | ES 的调研和集成应尽早启动（第 1-2 周），不要拖到后期 |

## 三、进度可行性分析

### 3.1 时间约束

| 约束项 | 说明 |
|--------|------|
| 总周期 | 约 6 周（1.5 个月） |
| 团队人数 | 3 人 |
| 可用工时 | 假设每人每周可投入约 15-20 小时，总工时 ≈ 270 ~ 360 人时 |

### 3.2 开发阶段划分

| 阶段 | 时间 | 主要任务 | 交付物 |
|------|------|----------|--------|
| **第 1-2 周**：设计 + 环境搭建 | 2 周 | 需求确认、数据库设计、接口定义、Docker 环境搭建、ES 调研、前端框架初始化 | 数据库建表 SQL、API 文档、项目骨架 |
| **第 3-5 周**：核心功能开发 | 3 周 | 用户/商品/分类/购物车/订单/支付 CRUD、商家后台、管理员后台、搜索（ES） | 可运行的 MVP |
| **第 6 周**：收尾 + 文档 | 1 周 | 销售报表、退款退货、联调测试、Bug 修复、答辩文档/PPT | 完整系统 + 答辩材料 |

### 3.3 人员分工建议

| 角色 | 人数 | 负责模块 |
|------|------|----------|
| 后端开发 A | 1 人 | 用户/认证/鉴权、商品/分类/SKU、ES 集成 |
| 后端开发 B | 1 人 | 购物车/订单/支付/退款、销售报表、WebSocket |
| 前端开发 | 1 人 | Vue 3 前端全部页面：商城布局 + 商家后台 + 管理员后台，Axios 封装，WebSocket 前端 |

> 备注：如果某人进度快，可交叉支援。ES 集成建议后端 A 和前端联调协作。

### 3.4 进度风险评估

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| ES 学习耗时超预期 | 中 | 搜索功能延期 | 先跑通基本搜索，自动补全等高级功能可后期补 |
| Docker 环境问题 | 中 | 开发受阻 | 允许先本地安装 MySQL/Redis 直接开发 |
| 前端工作量超预期 | 中 | 部分页面延期 | 先完成核心页面（商城购物流程），后台页面精简 |
| 期末其他课程压力 | 高 | 最后2周时间压缩 | 第 5 周前完成至少 90% 代码，第 6 周只做收尾 |

### 3.5 进度可行性结论

| 结论 | 说明 |
|------|------|
| ✅ **时间基本充足** | 6 周 + 3 人团队完成课程设计级别项目是可行的 |
| ⚠️ **需严格控制范围** | 低优先级功能（评论、即时通讯、搜索历史）必须果断裁剪，避免影响核心功能 |
| 📋 **里程碑关键** | 第 4 周末必须完成核心购物闭环（浏览→购物车→下单→支付），否则后续风险极大 |

## 六、综合可行性与建议

### 6.1 总体结论

| 维度 | 结论 | 置信度 |
|------|------|--------|
| 技术可行性 | ✅ 可行（有风险但可控） | 85% |
| 进度可行性 | ✅ 可行（需严格控制范围） | 80% |
| 经济可行性 | ✅ 完全可行 | 100% |
| 运行可行性 | ✅ 完全可行 | 95% |

**综合评价**：该项目在技术、进度、经济、运行四个维度上均可行，建议立项开发。

### 6.2 关键成功因素

1. **尽早启动 ES 学习与集成**（第 1-2 周），这是最大技术风险点
2. **严格遵守优先级**，低优先级功能（评论、即时通讯）在时间不足时果断裁剪
3. **第 4 周末达成购物闭环**（浏览 → 购物车 → 下单 → 支付），这是最重要的里程碑
4. **前后端并行开发**，前端先用 Mock 数据开发页面，后端接口就绪后快速联调
5. **Docker Compose 一键启动**，避免"在我电脑上能跑"的问题

### 6.3 主要风险与缓解措施汇总

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| ES 学习成本高 | ⚠️ 高 | 第 1-2 周专人调研；先跑通基本搜索，高级功能延后 |
| WebSocket 不熟悉 | ⚠️ 中 | 降为低优先级，核心功能完成后开发 |
| Docker 不熟悉 | ⚠️ 中 | 允许先本地直接安装中间件；中期补 Docker Compose |
| 期末时间压缩 | ⚠️ 中 | 第 5 周前完成 90% 代码；低优先级功能果断裁剪 |
| 前端开发量大 | ⚠️ 中 | 后台管理页面可简化样式，优先保证商城购物流程 |
| Redis 分布式锁 | ⚠️ 低 | 参考成熟方案，社区资料丰富 |
